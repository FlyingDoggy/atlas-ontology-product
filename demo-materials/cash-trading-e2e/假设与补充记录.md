# Cash Trading 假设与补充记录

本记录用于区分三类事实：Deloitte HK 明确提供的内容、产品为了演示做的标准化、产品为了跑通链路新增的构造内容。任何后续演示、复核或交付不得抹去这些边界。

## A. 原始材料事实

1. 业务场景为 Cash Market 的 Order and Trading Activity Monitoring。
2. 使用角色包括 Market Surveillance、Markets Team 与 Trading Team。
3. 业务过程覆盖日终订单与成交数据接收、常规报告、告警复核、管理层复核，以及临时洞察和新评估方法。
4. 分析链路描述为：原始接口文件进入 Data Platform，形成 parquet，经清洗和类型转换形成事实/维度与聚合指标，再进入 Dashboard 或报告表，由业务和管理层复核。
5. 需求材料包含 7 个分析问题和 8 个指标逻辑。
6. 数据字典包含订单活动、成交活动、证券、账户、交易日历、订单类型和汇率等模型。
7. 样例数据为构造数据。

## B. 可逆标准化

| 编号 | 标准化 | 原因 | 对原意影响 |
| --- | --- | --- | --- |
| N-01 | 展示语言统一为中文，稳定技术 ID 保留英文小写命名 | 避免同一 Ontology 中英文随机混排，同时保留可执行标识 | 无 |
| N-02 | `canceled` / `cancelled` 统一为产品合同中既有的 canonical spelling；原始词形保留在来源证据 | 避免字段和规则出现两个同义标识 | 无 |
| N-03 | 把一个物理 Excel 的需求页和指标页登记为两个逻辑来源角色 | Builder 需要明确区分需求证据与指标证据 | 无 |
| N-04 | 图片邮件只归档，不参加结构化自动抽取 | 图片内容主要说明材料来源和限制，且 OCR 结果不应自动升级为业务事实 | 无 |

## D. 待 Deloitte HK 确认但不阻塞 PoC 的事项

1. 各指标的最终业务 Owner、审批人和正式更新频率。
2. 数据字典 Overview 中部分字段数与具体 Sheet 可见字段数的差异，应以最终生产数据合同确认。
3. 订单、撤单、成交事件的正式状态枚举与 correction/cancellation 处理规则。
4. 指标中“active client”“potential self-trade”“eligible cancel”等业务口径的生产级边界条件。
5. 现有生产 SQL、实际物理表名、分区键和性能约束。
6. 汇率换算、交易日历、时区和跨日事件的正式规则。

上述事项在 PoC 中通过显式假设、Gap 或产品补充处理；不得悄悄伪装成已确认事实。
