# ADT 分析场景——需求与端到端流程（Reference Example）

> 状态：人工编写的合成参考材料，不含 customer 内部信息。

## 1. 业务背景与目标

市场分析师需要比较两个季度的总成交额和平均每日成交额（ADT），判断变化幅度，识别对总成交额变化贡献最大的市场板块，并能够解释数字采用了什么指标定义、数据字段和过滤条件。

本参考场景覆盖 2025-Q3 与 2025-Q4，市场范围为合成现金市场 `SYNTH-CASH`。

## 2. 用户与决策

- 主要用户：Market Analyst；只允许查看市场或板块级聚合结果。
- 次要用户：Executive Viewer；可查看已批准的聚合结果。
- 不允许：外部用户、逐笔成交明细、成交 ID 或证券 ID 的披露。
- 业务决策：确认总成交额下降的规模、ADT 变化以及下降主要来自哪个板块。

## 3. 业务过程

1. 上游交易系统产生逐笔成交记录，包含成交日期、证券、执行成交额、处理状态和取消标记。
2. 数据管理团队维护证券到市场板块的受控映射。
3. 市场运营团队维护交易日历，并明确每个日期是否计入交易日分母。
4. 报告任务按指定期间读取上述快照，应用合资格成交规则，计算成交额和交易日数，再计算 ADT。
5. 分析师比较两个期间，并按市场板块汇总成交额变化。
6. 结果发布前要完成字段映射、主键、关联基数、过滤规则、结果对账和权限检查。
7. 用户看到结论时，应同时能够查看定义、数据版本、执行计划、SQL 指纹和结果证据。

## 4. 端到端分析流程

用户提出问题 → 识别指标和两个明确期间 → 检查角色和粒度 → 绑定已发布的指标/字段/规则 → 生成受控查询契约 → 执行聚合 → 与独立预期结果对账 → 计算比较、板块贡献和顺序分解 → 返回结论与证据。

若缺少期间，应先澄清；若要求预测或逐笔明细，应在访问数据前拒绝；若数据校验或分母失败，不应生成结论。

## 5. 输入、范围和关键口径

- 输入：交易事实、证券维表、交易日历和现有 ADT SQL。
- 时间范围：2025-07-01 至 2025-12-31。
- 期间：2025-Q3、2025-Q4；不允许系统自行猜测季度。
- 合资格成交：`status = 'EXECUTED'` 且 `cancellation_flag = false`。
- 成交额字段：`executed_value_hkd_mn`，单位为百万港元；`order_value_hkd_mn` 不能用于该指标。
- 交易日：交易日历中 `is_trading_day = true` 的去重日期；有无成交均不影响交易日计数。
- 半日市：本合成样例按一个完整交易日计数；真实场景必须重新确认。

## 6. 期望输出（多条答案要求）

| 编号 | 用户问题/答案要求 | 最小输出 | 呈现形式 |
|---|---|---|---|
| O-01 | 各季度 ADT 是多少？ | 期间、合资格成交额、交易日数、ADT、单位 | 表格 + 一句结论 |
| O-02 | Q4 较 Q3 变化多少？ | ADT 绝对变化、百分比变化、总成交额变化 | 表格 + 方向描述 |
| O-03 | 哪个板块对总成交额下降贡献最大？ | 各板块前后值、变化、净变化占比、加总对账 | 排名表 + 结论 |
| O-04 | 总成交额变化可如何分解？ | 交易日效应、日均活跃度效应、残差、方法声明 | 瀑布数据 + 非因果声明 |
| O-05 | 这些数字为什么可信？ | 指标定义、过滤、映射、快照、SQL/结果哈希、校验状态 | 可展开证据 |

## 7. 验收条件

- 同一已发布快照和相同问题得到相同结果。
- Q3/Q4 的总成交额、交易日数、ADT 与独立 oracle 一致。
- 板块变化之和与总变化一致；顺序分解闭合，残差为零或在规定容差内。
- 改错金额字段、漏掉过滤条件、破坏日历或制造维表重复键时，发布/分析必须失败。
- 输出中不得出现逐笔数据或受限字段。

## 8. 已知限制与待真实场景确认

- 本场景只覆盖描述性、比较性和确定性分解，不声称因果关系，也不支持预测。
- 板块贡献定义为“板块成交额净变化 ÷ 总成交额净变化”；当总变化为零时拒绝计算。
- 顺序分解采用“交易日效应优先”，结果依赖顺序，必须披露。
- 真实项目需重新确认币种转换、跨市场范围、半日市、补录/冲销、晚到数据、公司行动及历史重算政策。
